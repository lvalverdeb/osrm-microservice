The question you asked

Yes — deployment itself is a days-scale exercise, not a project. Putting it into operation is a ten-week program, and it turns on two things this repository deliberately does not contain.

  1. The gateway has no authentication and no TLS, by design. gateway/src/openapi.rs states it and a test enforces it; the dependency list carries no TLS stack at all. Nothing here can face a network you do not fully trust until IT supplies an edge that terminates TLS and authenticates callers. That is the one genuine prerequisite, and it is not in scope of this codebase.
  2. The shipped /vrp is capacity and geography only. No time windows, no service times, no driver shifts or skills, and no time-of-day dimension anywhere — every plan assumes free-flow speed. If dispatch needs delivery windows, that is a build project, not a deployment. Confirm this in week one, before anything is provisioned.

Everything else is in the suite's favour. Both deployment paths are scripted end to end with health gates and are safely re-runnable. The stack holds no persistent state — Redis is a cache, losing it costs cache hits and nothing else — so there is no data migration to design, no backup schema, and no restore rehearsal. Rollback is redeploying the previous build. That is an unusually cheap operational profile, and it is why the ten weeks below are dominated by functional validation rather than infrastructure.

Trap, jail path only

net.inet.tcp.delayed_ack=0 is worth 67 ms → 9 ms on p50 latency, and it can only be set from the host. Skip make jail-host and the jail simply looks like slower hardware — nothing errors and nothing logs. Build the jail-doctor check into the provisioning checklist, not into someone's memory.

Conditions, constraints and known traps

Everything below is a real property of the system as it stands, confirmed against the source. Two are stop-ships; the rest are bounds to design within, and each one has an owner and a closing action.

 FindingConsequenceClosed byOwner
Stop-ship No authentication, no TLS anywhere in the gateway Cannot be exposed beyond a trusted network. Any caller who reaches the port gets the full API. Reverse proxy or API gateway terminating TLS and authenticating callers, built by IT IT-2
Stop-ship No time windows, service times, skills or shifts in /vrp; no time-of-day dimension at all If dispatch requires delivery windows, the shipped optimiser cannot express the requirement. Week-one fit-gap. Either accept capacity-and-geography planning, or scope a separate build. FN-1
Gate An L7 proxy without FORWARDED_ALLOW_IPS makes every client share one rate-limit bucket Rate limiting silently stops working per-client. Setting it to * defeats limiting entirely — any caller mints a fresh bucket per request. Set it to the proxy's CIDR and prove per-client buckets in load test IT-2
Gate One engine per routing profile. Three profiles means three map builds and three osrm-routed processes Roughly triples data-build time, disk and RAM. A 2 GB jail will not comfortably host three. Confirm required profiles in week one; size the host against that number IT-1
Gate No high availability in the repository. Single node, no clustering or failover Host loss is an outage. Two nodes behind a load balancer is possible — Redis shares the rate-limit counters — but nothing here builds or tests it. Accept single-node with a documented RTO, or fund an HA design IT-1
Bound Matrix capped at 10,000 cells (100 coordinates square) Wider matrices are refused. Raising it requires --max-table-size changed in both deployment definitions, as the square root. Size against real stop counts; change both files in one commit IT-4

Bound process_* metrics are read from /proc and are absent on FreeBSD CPU, RSS, open-FD and start-time panels will be blank on the jail path. Build dashboards and alerts that do not depend on them IT-5
Bound make process-osrm needs Docker even when the target is the jail A pure-FreeBSD shop still needs one Docker host, or must use make jail-data to build natively. Decide which; the jail path builds its own data and needs no Docker IT-3
Bound make help advertises build-pkg, publish and clean-pkg, none of which exist An engineer following the help text hits No rule to make target. They retired with the PyPI package. Note it in the local runbook; ignore those three lines IT-4
Bound Settings counts disagree across docs — 29, 35 and 36 in different places A config review driven from prose will miss settings. Review against gateway/src/config.rs, which is the single source of truth IT-4

The fast path, if you only need it on a trusted network

Strip the functional program away and a staging deployment is four to five working days of IT effort: half a day to provision, half a day for host prerequisites, a day for the map build, half a day to deploy and health-check, a day for configuration review, and a day for smoke and load testing. That is a legitimate first milestone — get it standing in week two, then spend eight weeks proving it belongs in the business.

Worth telling the functional team early

A straight line understates a real Costa Rica drive by roughly 40% at the median, and by 17.6× in the worst sampled pair — two points 914 m apart, 16.1 km by road. Two-thirds of metropolitan address pairs have a different distance out than back. Dispatchers who have been eyeballing a map will find plans counter-intuitive at first, and the plans will usually be right.

Read the load test carefully

A run reporting 100% transport errors at ~2 ms latency on every endpoint — including /health and /metrics — is pointed at nothing. That is connection-refused, not a service under stress. Check the URL and the published port before reading it as a failure. The load-test default URL is the jail's port; the Docker path needs it passed explicitly.

Assumptions, and what would change the plan

Stated so the schedule can be challenged on its premises rather than its arithmetic.

Assumed

  • One production environment plus staging, in one region, on one deployment path.
  • One routing profile at go-live. Each further profile adds roughly a day of build time and its own engine process.
  • An existing dispatch or order application to integrate with; no new user interface is being built.
  • Teams work the program part-time alongside existing duties — which is why elapsed weeks exceed the sum of working days.
  • IT can supply a reverse proxy or API gateway. Without that capability, add three to four weeks and treat it as a separate project.
  • Single-node operation is acceptable with a documented recovery time.

What would change the plan materially

  • Delivery time windows are required. The program becomes a development project. Rescope at G0 — do not attempt to work around it in dispatch procedure.
  • High availability is required. Add a two-node design, a load balancer, shared Redis for rate-limit counters, and the testing to prove failover. Nothing in the repository does this today; budget three to four weeks.
  • More than one region or map extract. Multiplies the data workstream and the host footprint; the gateway itself is unaffected.
  • Matrices wider than 100 coordinates. Requires an engine flag change in both deployment definitions, and re-measuring memory afterwards.
  • The FreeBSD jail is the target and it is memory-constrained. Build times lengthen considerably and the extract can meet the OOM killer. Add a week to the data and build workstreams.
