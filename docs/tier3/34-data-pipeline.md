# 34 — Data pipeline

*Tier 3: authored from the Makefile, `deploy/docker/Dockerfile.builder`,
`deploy/freebsd/install.sh`, `examples/tools/build_sample_slice.py`,
`examples/src/fleet/generate_delivery_dataset.py`.*

Two unrelated datasets. **Routing data** is the OSM extract the engine serves.
**Delivery data** is the synthetic corpus the examples and benchmarks run on.
Neither is committed at full size.

## Routing data

### The pipeline

```
Geofabrik .osm.pbf  →  osrm-extract -p <profile>.lua  →  osrm-partition  →  osrm-customize  →  .osrm files
```

`osrm-routed` is started with `--algorithm mld`, which is why partition and
customize are both required — MLD needs the cell hierarchy that `-partition`
builds and the weights `-customize` fills in.

### One graph per profile

One `osrm-routed` serves one built graph, so three profiles means running the
pipeline three times over the same `.pbf`. The two vocabularies meet at exactly
one place in each deployment:

| OSRM profile | Gateway profile | Docker service | Jail port |
|---|---|---|---|
| `car` | `driving` | `osrm-backend` | 5000 |
| `bicycle` | `cycling` | `osrm-backend-cycling` | 5001 |
| `foot` | `walking` | `osrm-backend-walking` | 5002 |

Getting that mapping wrong "points a profile at the wrong graph, which is the
failure the whole change exists to remove" — before the split, `profile=walking`
returned car routing byte for byte with nothing saying so.

### Fetching and building

```sh
make download-data     # curl $(GEO_URL) -> data/$(OSM_FILE)
make process-osrm      # build the builder image for $(PROFILE)
make compose-up        # builds all three profiles, then starts everything
```

Defaults are `PROFILE=car` and `OSM_FILE=costa-rica-latest.osm.pbf`, with
`GEO_URL` pointing at Geofabrik's central-america extract.

**Docker** requires the file locally: `Dockerfile.builder` does `COPY
./data/${OSM_FILE}`, so the build context must contain it. **The jail** can
fetch it itself when `GEO_URL` is set and nothing was staged — the only
substantive asymmetry between the two paths here.

Extracting is the slow part of a cold start: three passes over the same
extract, under binfmt emulation if the host is not arm64 (doc 32).

### Rebuilding after a map update

An OSM re-import invalidates more than the graph. `matrix_version` folds the
**extract version** into the hash a plan is pinned to (doc 19), so a re-import
means previously pinned plans no longer validate against a freshly built
matrix — by design, since INV-4 compares them. Speed-profile multipliers are
fitted *against the engine's assumptions*, so re-fitting after a map change is
mandatory rather than housekeeping (doc 31).

### The synthetic map

`tests/synthetic/` holds a tiny hand-made map that a real `osrm-routed` serves
during `tests/test_synthetic_routing.py`. The toolchain is not packaged for
Ubuntu, so those tests drive it through Docker and skip when the image is
unavailable; CI pulls the image in its own step to keep the pull out of the
first test's timeout.

## Delivery data

### Three artefacts, one of them committed

| Artefact | Size | Committed | Built by |
|---|---|---|---|
| `data/deliveries_cr.json` | ~12 MB, 50,000 stops | **no** | `examples/src/fleet/generate_delivery_dataset.py` |
| `examples/data/deliveries_sample.json` | small | **yes** | `make examples-slice` |
| `vrp/bench` corpus | — | generated | `make corpus` |

### The slice is not a sample

`examples/data/deliveries_sample.json` is what the examples fall back to when
the full corpus is absent — on a fresh clone, and in CI. Without a stand-in,
"every dataset-backed example skipped and the gate proved nothing about them".

The contract is precise, and it is not "a random tenth":

> A random tenth of the corpus would answer every selection differently and
> quietly change what each example prints. It is the *union of the slices the
> examples actually take*, so that every selection in `MANIFEST` returns the
> same deliveries, in the same order, as the full corpus.

`tests/test_sample_slice.py` checks that whenever the full corpus is present.
**What it does not cover is selections outside `MANIFEST`** — an example that
invents a new selection is not guaranteed to behave the same on the slice.

So: adding a dataset-backed example means adding its selection to `MANIFEST`
and running `make examples-slice`.

### Regenerating the corpus

The benchmark corpus is **regenerated by its own pipeline**, and patching a
committed corpus file by hand does not survive. Change the generator.

The corpus also passes the anonymisation gate on the way out (doc 30) — a
corpus derived from real deliveries cannot be written without it.

```sh
make corpus            # the P0 scenario corpus at all three sizes (slow)
make examples-slice    # rebuild the committed slice from the full dataset
make catalogue         # rebuild the scenario catalogue from its source markdown
```

## What is generated versus authored

| Path | Status |
|---|---|
| `data/*.osm.pbf` | downloaded; gitignored |
| `data/deliveries_cr.json` | generated; not committed |
| `examples/data/deliveries_sample.json` | generated, **committed**, checked by a test |
| `docs/TDD/vrp-catalogue-v2.1.md`, `scenarios.jsonl` | generated from `.src.md`, committed, checked |
| `docs/tier1/*.md` | generated, committed, checked |
| `benchmarks/instances/*` | published third-party instances, committed |
| `parity/fixtures/upstream/*.json` | recorded engine responses, committed |

Everything in that table with "checked" has a test that fails when the
committed copy stops matching a fresh build. The rest is reproducible on
demand.
