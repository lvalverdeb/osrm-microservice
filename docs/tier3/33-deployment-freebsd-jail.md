# 33 — Deployment: FreeBSD jail

*Tier 3: authored from `deploy/freebsd/`, the `jail-*` make targets,
`deploy/README.md`.*

The second supported option, for a jail on a FreeBSD host — **a jail cannot run
Docker**. The same three services run natively: `osrm-backend` and `redis` come
from FreeBSD packages using the rc.d scripts their own ports ship, and only the
gateway needs one of ours.

## The call path

The api jail runs **no sshd of its own** (the host's sshd binds `*:22` and
answers for the jail's address too), so every command takes this route:

```
make jail-*  →  ssh <host>  →  jailctl.sh  →  jexec  →  install.sh (inside the jail)
```

`jexec(8)` requires **real root on the host**. `jailctl.sh` detects root, then
`doas`, then `sudo`, and reports which without requiring any of them.

```sh
make jail-doctor   # identity, arch, memory, and which escalation method exists
```

If the login has none, the error names the fix: install `doas` and write
`permit nopass :wheel`, or install an SSH key for root and deploy with
`JAIL_HOST=root@<host>`.

## The targets, in the order you need them

| Target | Runs | Does |
|---|---|---|
| `jail-stage` | host | uploads sources, `deploy/freebsd` and `deploy/env`. **Implied by every other `jail-*` target** |
| `jail-doctor` | host | identity, arch, memory, escalation method |
| `jail-host` | host | kernel tunables, `jail.conf` loopback, jail resolver |
| `jail-bootstrap` | jail | installs packages, creates the service user |
| `jail-data` | jail | builds the OSRM graphs in the jail |
| `jail-up` | jail | builds and installs the gateway, (re)starts all three services |
| `jail-health` | jail | runtime checks for API and OSRM |
| `jail-logs` | jail | tails the gateway log and system messages |
| `jail-down` | jail | stops all three |
| `jail-publish` | host | redirects the host's port to the jail's gateway (edits `pf.conf`) |
| `jail-unpublish` | host | removes that redirect |

A first deployment is `jail-host` → `jail-bootstrap` → `jail-data` → `jail-up`.
Every phase is idempotent and safe to re-run.

## Why `jail-host` exists

Three host-level things the jail cannot do for itself:

1. **Kernel tunables** (`sysctl`, persisted).
2. **A loopback address for the jail** — `ip4.addr += "lo1|127.0.0.1"` in the
   host's `jail.conf`. This one matters more than it looks; see Redis below.
3. **A resolver for the jail**, because `cargo` must fetch crates.

## Configuration

Same two tiers as Docker, assembled differently. `install.sh` writes
`${JAIL_DIR}/.env` as:

```
<deploy/env/app.env verbatim>            # the shared block, identical to Docker's
# --- generated by install.sh; overrides the shared block above ---
OSRM_BASE_URL=…  OSRM_URL_*=…  REDIS_URL=…  FORWARDED_ALLOW_IPS=…
```

**The overlay wins because it comes last**: the binary's `.env` parser takes the
last occurrence of a duplicated key, matching pydantic-settings.

`OSRM_API_URL` deliberately stays at the shared value — it is a *client-side*
setting (`examples/` reads it to find the gateway), not a server one. The bind
address is not written either; the rc.d script passes it through
`${name}_env`.

Every jail knob is `JAIL_`-prefixed on purpose. The Makefile exports its whole
environment, so an unprefixed `OSRM_BASE_URL` would leak a developer value into
the jail; `install.sh` strips the prefix on the far side.

## The gateway is built in the jail, under a different cargo profile

```sh
cargo build --profile jail --locked
```

The `jail` profile is thin LTO across 16 codegen units. The default release
profile is fat LTO in a single unit, "which is the most memory-hungry way to
build and can meet the OOM killer on a 2 GB box shared with two other jails".

Root owns the installed code and the service user only reads it (`chown
root:osrmapi`, `chmod 750`, `.env` `640`), so **the gateway cannot rewrite its
own binary or configuration at runtime**.

## The rc.d script, and four things it gets right

`deploy/freebsd/osrm-api-gateway` runs the binary under `daemon(8)`.

- **The tracked pid is `daemon(8)` itself**, the supervisor. SIGTERM to it reaps
  the child and exits without restarting, so `service osrm_api_gateway stop` is
  clean.
- **No `-u`**: `osrm_api_gateway_user` is `${name}_user`, which rc.subr expands
  into `su -m … -c` around the whole command, so `daemon(8)` already runs as
  that user. Passing `-u` as well fails in the child, where
  `restrict_process()` calls `setusercontext(LOGIN_SETALL)` and that needs root.
- **Only three values go through `${name}_env`** (`HOST`, `PORT`, `WORKERS`).
  rc.subr expands it unquoted into an `env …` prefix, so a value containing `;`
  would terminate the command — and `HEALTH_CHECK_COORDS` is `0,0;0,0`.
  Everything else reaches the binary through `.env`.
- **`FORWARDED_ALLOW_IPS` is in `.env`, not a sysrc knob**, for the same
  expansion reason: the value `*` would glob against the working directory.

The `precmd` is the last thing that runs as root, and it pre-creates both
pidfiles and the logfile owned by the service user — `daemon(8)` is
unprivileged by the time it opens them and `/var/run` is not writable by that
user.

`osrm_api_gateway_chdir` is the app directory, because the binary reads `.env`
from its working directory.

## Restarting a service never uses a bare `service … restart`

Everything goes through `restart_service()`, which captures output to a temp
file. The reason is specific and would otherwise be baffling:

> `daemon(8)` would start the new child with this script's stdout still
> attached, and over ssh that is the session's pipe, so ssh would hang until
> the daemon exits — which is never, for a service — and fail with its own 255
> long after the work had finished.

## Redis, and the jail loopback trap

Config is layered on the port's own (`include /usr/local/etc/redis.conf`) so
package updates still flow, installed as `redis-osrm-cache.conf` and selected
with `sysrc redis_config=…`.

Two directives differ:

- `save ""` / `appendonly no`, mirroring Docker's cache-only posture. With the
  port's default `stop-writes-on-bgsave-error`, a failed fork on a small box
  would make Redis start refusing writes — "turning a cache miss into an
  outage".
- **`protected-mode no`**, and the reason is the subtle one:

> A jail has no per-jail loopback source address: a client inside the jail
> connecting to 127.0.0.1 still leaves with a source of `ip4.addr`, so redis
> sees a non-loopback peer and protected mode answers DENIED to every command.
> That silently disabled the L2 cache and the rate limiter's shared storage.

Turning it off is safe **because** the listener is bound to the jail's real
loopback — the `ip4.addr += "lo1|127.0.0.1"` that `jail-host` arranges. Sibling
jails cannot reach it on either address.

## Routing data

`jail-data` builds one graph per profile in the jail, at `/var/db/osrm-backend/
<profile>/`. Profiles are `car::5000 bicycle:_cycling:5001 foot:_walking:5002`
— OSRM profile, rc.d suffix, jail-local port. **The suffix is empty for car** so
the existing `osrm_routed` service, its rc.conf keys and anything already
watching them keep their names.

Unlike Docker, the jail can **fetch the extract itself**: set `GEO_URL` and it
downloads when no local `data/*.osm.pbf` was staged.

## Publishing

`jail-publish` edits the **host's** `pf.conf` to redirect the host port to the
jail's gateway; `jail-unpublish` removes it. Both need host root.

## What differs from Docker

| | Docker | Jail |
|---|---|---|
| gateway build | `--release` in a builder stage | `--profile jail` natively, in the jail |
| engines | one container per profile | one rc.d service per profile, ports 5000–5002 |
| redis | container, cache-only flags | port package + layered conf, `protected-mode no` |
| metrics | `process_*` present (Linux `/proc`) | **absent** — FreeBSD has no `/proc` by default |
| extract | requires a local file | can fetch via `GEO_URL` |
| restart | `docker restart` | `restart_service()`, never bare `service restart` |

## Known staleness

`deploy/freebsd/.env.example` describes `JAIL_API_WORKERS` as "uvicorn bind and
worker count" and says workers > 1 "makes the rc.d script export
`PROMETHEUS_MULTIPROC_DIR`". The rc.d script's own header says the opposite and
is current: that knob is gone, because workers are threads in one process. The
same stale wording appears in the Makefile's `JAIL_FORWARDED_ALLOW_IPS` comment.
