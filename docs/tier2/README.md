# Tier 2 — Architecture and behaviour

**Tier 1 is what the sources can state about themselves. Tier 2 is what they
cannot.**

Every document here is authored: it explains a mechanism, the decision behind
it, and the failure the decision prevents. That is not derivable, because the
reasoning lives in prose — module docstrings, comments above a dependency, a
measurement recorded next to the constant it justifies — and joining it into an
account of how the system works is a judgement.

What they are not is invented. Each document cites the files it was read from,
and a claim that could be checked against a running system was. Where the code
does not answer a question, the document says so rather than filling the gap.

## Reading order

**New to the system:** 14, then 23 to see what it can model, then 20 and 21 for
how a plan is produced and checked.

**Operating it:** 15, 16, 17, 18 — the gateway's behaviour under load, and what
it reports about itself.

**Integrating against it:** 18 for the versioned surface, then
[doc 01](../tier1/01-api-reference.md) for the endpoints and
[doc 21](21-invariants-and-verification.md) for `/verify`. [Doc 42](42-endpoint-guide.md)
is doc 01 worked through — the same endpoints with a real request and the real
response it returned — and [doc 41](41-vrp-library-api.md) is the equivalent for
callers importing the library rather than calling HTTP.

**Deciding whether it fits an operation:** [doc 40](40-what-the-vrp-does.md)
explains what a vehicle routing problem is, then separates what the shipped
`/vrp` endpoint does from what the library does. It is the one document here
written to be read by someone who is not an engineer.

**Extending the model:** 22 (what "better" means), 23 (what exists), 21 (what
must still hold), then the constraint-specific documents 25–27.

## Maintenance

These are **not generated**, and no target rebuilds them (40–42 included;
their executed captures are a record of one run, not a live read). When a mechanism
changes, the document describing it must change with it; nothing in the suite
will notice if it does not. Tier 1 carries that guarantee instead — every table
it holds is regenerated by `make tier1` and checked by
`tests/test_tier1_docs.py` — which is why anything mechanically derivable was
left there rather than repeated here.

Two conventions keep the two tiers from drifting into each other:

- **A fact with a single source of truth in code belongs in Tier 1.** If you
  find yourself pasting a field list, a setting default or an endpoint table
  into one of these documents, link to the generated one instead.
- **A quotation from the code is a citation, not a copy.** Where a document
  quotes a comment, it is because the reasoning in that comment is the content
  — and if the comment changes, the quotation is wrong and should be updated.

## Open questions these documents surfaced

Raised while reading, not resolved here:

1. **No authentication or authorization exists in the gateway.** Whether that
   is a trusted-network posture or a gap is not recorded anywhere (doc 14).
2. **`/nearest/batch` is served unversioned but carries no deprecation
   advisory**, unlike the other eight data-plane endpoints (doc 18).
3. **Responses produced by an outer middleware carry no advisory**, so a
   rate-limited client is never told to migrate (doc 18).
4. **The comment on `catch_panic` claims an ordering the layer stack does not
   appear to give it** — if correct, a panicking request is not counted
   (doc 14). Not reproduced; needs a panic path to confirm.
5. **`vrp/api.py`'s window parser drops both soft-window cost rates**, recorded
   in `vrp/servicemodel.py` (doc 21).
6. **`VRP_MAX_QUEUE_DEPTH` ships at 0**, which disables the bound added to stop
   overloaded callers paying a full 10-second timeout before being refused
   (doc 16).
